# Can a mailbox scanner connect a forwarded price to its source?

A fictional supplier offer and a public market benchmark both read **$42.61**. An analyst forwards the same workbook in two different emails. Which copy should a reviewer flag, and which hidden cell supports that decision?

Five systems reviewed 95 fictional email families under an explicit exercise policy. **Claude Haiku 5.5 identified all 42 controlled families, raised zero false alerts on 46 ordinary families, and identified all seven unresolved families.** On the nine hardest pairs, it got both decisions right and cited the exact source and value every time. GPT-6 Luna passed six of those nine. Nemotron 3.5 Bolt E4B, Qwen2.5 14B and the JEPA-style entrant each passed zero. This measures the decision after extraction. The benchmark supplies underlying worksheet values, recovered PDF text and OCR to every entrant.

## The experiment

The November checkpoint review compares four-family classification, single-family classification, and extracting record identifiers before comparison. The second 16-email probe changes the wording and includes document paragraphs. [Checkpoint selection and trial results](MODEL-SELECTION.md)

The complete public round has 95 synthetic RFC822 emails, 42 controlled, 46 ordinary and seven unresolved. The main track has 33 matched pairs plus 11 legacy practice cases. A second track adds nine harder pairs. Of the 42 pairs, 36 have opposite verdicts. The remaining six check whether removal or an absent attachment changes what can be inferred. Public historical email is outside this release. Every native email used in these scores ships with it.

The main track covers visible, hidden and very-hidden XLSX sheets, inline and quoted body text, Word paragraphs, text PDFs, image-only PDFs, incremental white overlays, properly removed PDF content and missing attachments. The legacy cases add changed marking, misspelled quoted text, copied attachments, successive revisions, a storage floor and a bidder ranking. Across the new templates, the same CUI, privacy or absent banner occurs on both sides of a pair. The generator varies the target row and includes a decoy.

In the harder track both messages contain exactly the same words, including *sealed supplier bid* and *public benchmark*. Both attachments have the same SHA-256. The booked register includes only two of the three lots mentioned in the email. Swapping which lot is under seal makes one delivered family controlled and the other ordinary. The scorer requires a pointer to the quoted provenance and the actual numeric cell or PDF page. The two members of a pair never appear in the same prompt. This tests a relationship that keyword counts and attachment hashes alone cannot resolve. Each pair describes alternative fictional circumstances.

## What didn't work out

One example shows why the file hash cannot decide the answer. The hidden sheet records Lot 199 at $42.61 in Register!B2. In one forward, Lot 199 is the sealed offer. In the other, the sealed offer belongs to Lot 245, which is absent from the workbook. Both copies have the same bytes. [Sealed-lot EML](data/binding/mail/e8f65d5aff65.eml) · [Public-lot EML](data/binding/mail/c51c5ceb3b71.eml)

- **The frozen JEPA-style model could not connect the source note to the hidden cell.** It scored individual lines or rows, then selected the strongest candidate. It produced only one pointer. That interface alone prevents a dual-pointer success, so we also scored verdicts independently. It got both verdicts right on zero of nine binding pairs and returned the exact positive value on only five of 42 positive families overall. Its 0.83 seconds of scan time makes it inexpensive, but dropping mail on its negative verdict would have lost 15 controlled families. The result applies to this small model trained on 48 synthetic contexts. [JEPA implementation](latent_model.py) · [Per-message outcomes](scores/ema.json)
- **Bolt's perfect recall masked substantial review work.** It flagged all 42 positives, also flagged 15 ordinary families, and correctly called just one of seven unresolved cases. It often included a filename in the pointer or labeled quoted provenance as body text. Even when locator syntax was ignored it failed to get both verdicts right on any of the nine binding pairs. Its 45.6 seconds on the 4090 makes it a local candidate for producing review candidates, with substantial human verification. [Bolt outcomes](scores/bolt.json)
- **Qwen's structured output still lost records.** Only 91 of 95 families had a valid uniquely keyed row. It found 33 positives, reported 28 false alerts and sometimes returned the price itself in the locator field. The judge leaves missing or invalid entries in the denominator. It failed all nine binding pairs on verdicts alone. [Qwen outcomes](scores/qwen.json)
- **Luna was conservative around removed evidence.** It got all 42 positives and 39 exact positive value locations. It got zero of six removed-PDF verdicts correct. It sometimes prefixed an otherwise correct worksheet address with an extra `sheet!`. Nine ordinary families were called unknown, which matters for reviewer workload even though those do not count as controlled false alerts. [Luna outcomes](scores/luna.json)
- **Haiku's two misses were pointer-format errors.** For the visible sheet in case `090364ef0e07` and the native PDF in `8c732fbfc0ec`, it found the right value but returned `quote:paragraph:2` for a source whose defined locator was `quote`. These count as strict failures. Its binding-track successes include all six hidden-workbook pairs and all three PDF pairs. [Haiku outcomes](scores/haiku.json)

## Recommendations

Use Haiku as the reference reviewer for the next independently authored blind round. Luna is a credible lower-cost comparator where an unknown result can enter a review queue. Require the system to emit evidence IDs selected from the parser's actual locator inventory. Validate each returned pointer and flag invalid ones for review. Preserve original model outputs when evaluating that change so normalization cannot hide a wrong row or source.

Cache extraction by attachment hash. Cache a handling decision only when the governing policy and relevant email provenance also match. The binding pairs give a direct counterexample to caching the verdict by file hash. If local processing is required, evaluate a deterministic join between referenced lot IDs and native spreadsheet rows alongside Bolt, before using a local model to exclude messages from review. No tested local entrant supplied reliable automatic clearance on this dataset.

## RTX 4090 versus 128 GB DGX Spark

The measured desktop uses an RTX 4090 with 24 GB VRAM, an i9-9900K and about 48 GiB of host RAM. Bolt used one resident Q4_K_M model with four concurrent requests. It processed the frozen packets at **125 families/minute and 123 aggregate output tokens/s**. Qwen used one local Ollama client. Both fit on this system. The completed tests provide no Spark measurement on this mailbox.

The 128 GB GB10 Spark has a 20-core Arm CPU and 273 GB/s unified memory bandwidth. The RTX 4090 has about 1 TB/s dedicated GPU memory bandwidth. Spark can keep larger weights and more simultaneous contexts resident. Its CPU, GPU and runtime share the 128 GB. A small resident model can favor the 4090 during bandwidth-limited decoding. The Spark's advertised 1 PFLOP FP4 peak cannot predict time per reviewed family. Moving the same model to more memory is unlikely by itself to repair incorrect joins or evidence pointers. [NVIDIA Spark specifications](https://www.nvidia.com/en-us/products/workstations/dgx-spark/) · [NVIDIA Ada architecture](https://images.nvidia.com/aem-dam/Solutions/geforce/ada/nvidia-ada-gpu-architecture.pdf)

NVIDIA measured 38, 47 and 53 aggregate generation tokens/s at one, two and four concurrent requests on Spark running Qwen3 Coder Next FP8 with 32K input and 1K output tokens. Those settings differ materially from these short emails. Keep the 4090 for this prototype. Before buying the Spark, run the same GGUF and packets on its Arm CUDA build, sweep concurrency, then test whether a larger Spark-resident reviewer improves binding accuracy at the same false-alert budget. Separately time native extraction and OCR. [NVIDIA Spark throughput study](https://developer.nvidia.com/blog/scaling-autonomous-ai-agents-and-workloads-with-nvidia-dgx-spark/)

## Scope of the findings

These figures describe one disclosed synthetic practice set with few independent templates. They do not estimate prevalence, legal CUI status, real contractor recall or end-to-end PST scanning speed. Producers deliberately made counterpart files identical and used an exercise policy that made their source decisive. A new release should hold out whole projects, writers and forward chains, include larger workbooks and independently adjudicate ambiguous cases. A perfect result here warrants a blind test on new material. The corpus and scores are public for replication. Future evaluations should use fresh held-out cases.
